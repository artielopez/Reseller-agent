## Verified result

On the existing Reseller Agent Supabase project, one SQL session and one PostgREST HTTP session contended for the same synthetic work. The SQL session called the production worker RPC as `anon`, then held the transaction open. Before committing, it observed a different backend PID with `wait_event_type = Lock` and its own PID in `pg_blocking_pids`. This establishes actual overlap; launching promises or comparing timestamps alone would not.

| Operation                                | SQL result       | Competing HTTP result       | Durable outcome                    |
| ---------------------------------------- | ---------------- | --------------------------- | ---------------------------------- |
| Two enrolled workers claim one job       | Leased           | `null`, HTTP 200            | One lease                          |
| Two calls start the winning lease        | `admitted: true` | `admitted: false`, HTTP 200 | Exactly one app attempt            |
| Two identical submissions for that lease | Reply ID         | Same reply ID, HTTP 200     | Exactly one unapproved Agent Draft |

Final read-back: job Completed, attempt started, one usage reservation, one reply, no approval timestamp, inquiry Open. This was a fixed synthetic reply; no model was invoked, no allowance was used, and no marketplace was accessed. The database's app-attempt counter is not evidence of provider usage or a charge.

The successful run was 2 November **20:04:09–20:04:51 UTC** (3 November **04:04:09–04:04:51 Manila**). Observed lock contention in all three phases. An earlier invalid-token HTTP probe returned 401 / `42501`.

## Repeating the check

This is an operator procedure, not a migration, CI job or app feature. It temporarily commits synthetic rows so other sessions can see them. Retain the fresh owner UUID before setup and run guarded cleanup in a `finally` path, including after an uncertain response. Never substitute a real user's UUID or publish filled templates.

Files: [`scripts/acceptance/hosted-concurrency/`](../scripts/acceptance/hosted-concurrency/).

1. Verify the exact project and its six required migrations. Create a fresh UUID and substitute `__OWNER_ID__` in `setup.sql`. Execute the whole file. Keep the returned fixture, two worker tokens and record IDs in private operator memory. Setup commits; it is not rollback-only.
2. For **claim**, use worker A for `held-session.sql` and worker B for the peer. Command: `{"op":"claim"}`.
3. Write `{ "worker_token": "<peer token>", "command": <command> }` to the ignored `.worker-state/hosted-concurrency.json`, creating it exclusively with mode 600. Use the public project URL/key from ignored `.env.cloud.local`; do not use a service-role key.
4. Launch `node scripts/acceptance/hosted-concurrency/http-peer.mjs --delayed` as a retained background command. Confirm the process is live and has emitted `ready: true`, then immediately execute the whole held-session SQL with worker A's token and the exact JSON command substituted. The six-second delay exists solely to coordinate this test. SQL observes blocking and finishes within its 20-second timeout; HTTP has its own 20-second timeout.
5. Await both actual handles. Require a different blocked PID pointing to the held session and HTTP 200. Require exactly one lease; retain its job/lease IDs privately. If overlap was not observed or a response failed, stop and reconcile; do not count sequential success as a concurrency pass. Remove the private input file only after the peer stops.
6. Repeat steps 3–5 for **start**, both calls using the winning worker and `{ "op": "start", "job_id": "<job>", "lease_id": "<lease>" }`. Require true/false admission. Then repeat for **submit**, adding identical synthetic `body` and `review_reason` to both calls; require identical reply IDs. Complete within the existing 60-second lease. Do not lengthen production leases to make this check pass.
7. Run `verify.sql` with the retained UUIDs; require its one result to match the expected values in the comment. Run `cleanup.sql` with only this fixture owner UUID and require all counts zero. Remove private inputs, discard capabilities, and check that no peer process is still running. If interrupted, cleanup remains mandatory; report any leftover fixture rather than hiding it.

The peer is deliberately bound to this project and has no model or send function. It suppresses unexpected claim context and prints only error codes, never response error text or credentials. Its input is a temporary synthetic worker capability, not an app-user session.

## Harness corrections and limits

The first setup response parser accidentally matched the warning's quoted delimiter instead of the data block. Cleanup executed; a separate read verified zero fixture users/jobs/workers. The parser was corrected before continuing.

Two approaches did not establish overlap: parallel MCP SQL calls ran sequentially; launching HTTP through another tool while the SQL call was pending also failed to show contention. Both fixture sets were fully cleaned up. A direct Node REPL HTTP probe could not reach the endpoint. Starting a real delayed shell process **before** the SQL call resolved coordination and produced the passing lock observations above. None of these unsuccessful attempts is counted as acceptance.

Ruling: test the existing transaction guards against real PostgreSQL concurrency without changing production code to manufacture a failing baseline. This is acceptance/characterization evidence. Cost if insufficient: races involving pause/revoke, quota exhaustion, item edits and multiple competing jobs still require their own concurrent hosted checks. This run covers one job's claim/start/identical-submit path, not every race.

Also outstanding: physical Mac sleep/restart, actual provider expiry, two-user/device checks, ten-photo browser upload, outage alerts, permitted message intake and confirmed platform delivery. No unattended release, merge or sending is authorized by this result.
